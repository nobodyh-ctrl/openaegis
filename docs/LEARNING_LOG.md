## 3. Predicciones del `PATCH`

- *Si no se cambia el handler a `handler.lambda_handler` después de subir el zip, ¿qué error aparece?* Respuesta del usuario (2026-10-13): "no se encuentra el archivo del handler, un 404". **Idea central correcta**; corregido el detalle: no es un 404 HTTP sino `Runtime.ImportModuleError` (Lambda no encuentra el módulo `lambda_function`), la invocación falla antes de ejecutar el código y el cliente recibe un **500**.
- Predicción del upsert: el usuario pidió la explicación ("no sé, decime") y se le dio (ver error 15).
- Unicidad del `code` al editar: el usuario respondió bien que `S3-001` → `{"code": "S3-004"}` da **409** (encuentra a **otro** control).
- *Sin statement en la resource-based policy, ¿quién responde?* El usuario eligió bien: API Gateway responde 500 y la Lambda no deja logs.
- *¿Un `POST` a una ruta borrada de API Gateway deja log en la Lambda?* El usuario predijo que sí; **no**: el 404 `{"message":"Not Found"}` lo genera API Gateway sin invocar la Lambda. Hay dos 404 distintos: el de API Gateway (la ruta no existe en la API) y el del router de `handler.py` (la ruta existe en la API pero no en `ROUTES`).
- *Etapa 7: ¿por qué `implicitDeny` y no `explicitDeny`?* El usuario eligió la b ("la v2 tiene un Deny"), con la pista no supo; se explicó: la v2 solo tiene `Allow`, así que es el deny by default.

- *Etapa 8: con error pages, ¿qué status recibe el navegador en `/app/controles/abc/editar` si `abc` no existe?* El usuario eligió la b (403); con la pista, la c: **200**, y el 404 lo da después la API. *¿Por qué configurar el 403 y no solo el 404?* No supo; se explicó: sin `s3:ListBucket`, S3 responde 403 a lo inexistente (anti-enumeración).
- *Etapa 8: ¿qué ganamos al no usar `--delete`?* Primero respondió "un rollback"; con la pista: la pestaña abierta con el `index.html` viejo sigue pudiendo bajar sus chunks (si no, recibiría HTML por la regla de la 8.7). Atribuyó el 403 a la API: lo da S3.

- *Etapa 9 (9.1): callback solo de CloudFront y login desde localhost.* ✅ b: Cognito rechaza con `redirect_mismatch` antes del login. *Contraseña filtrada: ¿qué le falta al atacante?* "El MFA, para el token": idea correcta; corregido que el MFA es un paso del login, anterior a cualquier token.
- *Etapa 9 (9.2): saltear el CORS y mandar el token.* ✅ b: el navegador corta en la preflight y la Lambda no deja logs. *Con el CORS listo, ¿`curl` sin token recibe los controles?* ✅ Sí: CORS lo aplica el navegador.
- *Etapa 9 (9.3): `code` robado sin el verifier.* ✅ b. *¿Por qué no mandar el ID token a la API?* "Es para la app de login": correcto; se completó con datos personales y falta de `scope`.
- *Etapa 9: refresh token robado a las 10:00.* ✅ "hasta las 22:00". *¿Cómo cortarlo antes?* Con la pista respondió qué hace la revocación por dentro, no la acción; se explicó: cerrar sesión (revoca) o `admin-user-global-sign-out`, y el access token sigue hasta 1 h.
- *Etapa 9: pedir `scope: "openid email phone"` sin `phone` en el app client.* Respondió que se ignora (a); con la pista, mantuvo la a. Correcta: **b**, `invalid_scope` antes del login.
- *Etapa 9: el logout no llega al `/logout` de Cognito.* ✅ b: la cookie de Cognito te deja pasar sin contraseña. *Callback adentro de `/app`.* ✅ b: bucle. *`returnTo` a un sitio externo.* ✅ el usuario cae en el sitio falso (open redirect).
- *Etapa 9 (9.4): JWT firmado con otra clave.* ✅ b: `401`. *`DELETE` sin authorizer.* ✅ cualquiera borra con `curl` (matiz: necesita el `id`, pero un UUID no es control de acceso).
- *Etapa 9 (9.5): access token después del logout.* ✅ predijo `200` y dio `200`. *Sin el freno de 1 minuto.* ✅ bucle de login infinito.
- *Etapa 9, checkpoint:* compañero nuevo ✅ (b: lo crea el admin); bot sin token: primero el throttling, con la pista ✅ el JWT authorizer; dominio nuevo con error de CORS ✅ (Allow-Origin); robo con `global-sign-out`: primero "12 h", con la pista ✅ 1 h (el access token).
